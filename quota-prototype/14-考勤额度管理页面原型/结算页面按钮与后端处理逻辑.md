# 假期结算页面按钮与后端处理逻辑

## 1. 口径与边界

本文按本地 OEHR 代码快照反查，说明年假结算、病假结算、调休假结算页面中每个按钮点击后的现有后端处理。开发前需再与生产分支的接口、枚举值和配置项核对。

原型与当前 OEHR 只有一处有意差异：原型为撤销结算增加二次确认；这只是前端防误操作，不改变原有撤销接口和后端规则。

## 2. 通用处理流程

1. 用户在页面填写范围或勾选结算记录。
2. 前端执行必填和勾选校验；部分操作还会先调用专用校验接口。
3. 结算接口提交后进入异步任务。接口返回成功只表示任务已提交，不代表所有员工均处理成功。
4. 后端按员工或结算记录逐条校验，可以产生部分成功、部分失败。
5. 校验通过后，后端写入结算汇总、结算明细和操作日志，再更新额度余额或调休日明细。
6. 需要影响考勤结果的操作会触发考勤核算包重算。
7. 系统生成成功/失败明细文件，并向操作人的消息中心发送结果。

## 3. 按钮与接口对照

| 页面 | 按钮 | 接口 | 返回特征 |
| --- | --- | --- | --- |
| 年假结算 | 过期结算/离职结算 | `POST /api/attendance/vacationSettlementSummary/settlement` | 公共入参校验后异步逐员工处理 |
| 年假结算 | 撤销结算 | `POST /api/attendance/vacationSettlementSummary/cancelSettlement` | 提交异步撤销，消息中心返回最终结果 |
| 调休假结算 | 余额结算 | `POST /api/attendance/attendance-compensatory-leave-settlement-summary/balanceSettlement` | `@SysAsyncJob` 异步任务 |
| 调休假结算 | 离职结算 | `POST /api/attendance/attendance-compensatory-leave-settlement-summary/dimissionSettlement` | `@SysAsyncJob` 异步任务 |

## 4. 年假结算

### 4.1 过期结算

**页面入参**

- 年度范围：必填。
- 划分区域：必填。
- 结算额度所属日期：必填。
- 员工或组织：作为处理范围；未指定时，按区域及权限内人员处理。

**后端处理**

1. 校验结算类型、年度、所属日期和划分区域。
2. 根据员工/组织/区域查询员工，并检查用工记录、假勤方案和年假结转结算规则。
3. 进入异步任务后，先重新计算员工年假，再取指定年度范围的年假余额记录。
4. 逐员工校验：
   1. 不允许对该次入职日期之前的数据执行结算；
   2. 所属假勤方案必须配置可执行过期结算；
   3. 必须有年假余额记录；
   4. 结算额度所属日期的考勤数据不能已封存；
   5. 操作人必须对该员工有数据权限。
5. 每个年度的待结算额度 = `已失效总额度 - 已过期结算额度`，避免重复结算。
6. 当方案配置“按条件结算”时，后端会继续按年假最小单次时长校验；不满足条件时，本次结算额度为 0。
7. 合计结算额度小于等于 0 时，该员工记为失败，不生成有效结算。
8. 对成功员工保存结算汇总和按年度的结算明细，将每年结果回写到年假余额的“过期结算额度”，然后重新计算可休额度。
9. 记录年假结算日志，异步重算考勤核算包，并发送包含成功/失败人员的反馈文件。

### 4.2 离职结算

**与过期结算的差异**

1. 结算额度所属日期不接收管理员手工填写，后端直接取员工离职日期。
2. 员工必须已离职并存在离职日期。
3. 假勤方案必须允许年假离职结算。
4. 同一用工记录已有有效离职结算时，不允许重复结算。
5. 每个年度的结算额度直接取该年度当前可休额度，再汇总为结算总额度。
6. 年假余额回写“离职结算标识”和“离职结算额度”，并重新计算可休额度。

### 4.3 撤销年假结算

1. 前端传入勾选的结算汇总 ID；空集合或查不到结算记录时直接失败。
2. 后端查询当前最新用工记录和员工信息，然后异步处理。
3. 撤销前先重新计算员工年假。
4. 逐条排除：已撤销记录、结算所属日期考勤已封存、员工当前用工记录与原结算用工记录不一致的记录。
5. 对可撤销记录将结算汇总设为无效，写入撤销日志。
6. 后端重新汇总当前仍有效的结算明细：
   1. 过期结算重算各年度“过期结算额度”；
   2. 离职结算重算“离职结算标识/额度”。
7. 重新计算可休额度和考勤核算包，消息中心返回可撤销与失败明细。

## 5. 调休假结算

### 5.1 余额结算

**页面入参**

- 考勤周期：必填。
- 考勤时间段：必填，现有页面限制为单选一个周期时段。
- 员工/组织：可指定处理范围；未填时处理周期范围内匹配人员。

**后端处理**

1. 调用调休周期汇总“重新计算”流程，在每批重算完成后进入结算回调。
2. 取所选周期时段内的调休假日明细和员工调休假配置。
3. 考勤周期已封存的员工不处理。
4. 逐条按加班类型判断方案是否开启结算，并读取该类型配置的 OT 折算项。
5. 结算前重新汇总已有同类型结算额度，得到当前应结算的可休额度，写入结算明细和 OT 明细。
6. 清理该周期时段内的旧结算汇总/明细，保存本次有效结果，生成结算汇总和结算日志。
7. 建立“调休日明细—结算明细”关联，回写已转加班费额度，再刷新日明细、周期汇总和年度汇总。
8. 最终结果通过消息中心返回；全部人员周期已封存时，结果消息会按全部封存场景处理。

### 5.2 离职结算

1. 根据选中员工查询当前用工信息和调休假配置。
2. 前置校验：
   1. 员工所在区域必须开启调休假配置；
   2. 员工必须有有效离职单和最后工作日；
   3. 最后工作日必须能匹配可用考勤周期；
   4. 最后工作日必须存在排班。
3. 取员工全部“可休额度 > 0”的调休假日明细。
4. 员工最后工作日所在考勤周期已封存时，该员工跳过不处理。
5. 按加班类型检查“离职结算”配置，只结算配置为允许结算的可休明细。
6. 按 OT 配置计算转加班费结果，生成结算明细、OT 明细和结算汇总。
7. 建立每条原始调休日明细与离职结算的关联，将原可休额度转入已转加班费额度，刷新日/周期/年度汇总。
8. 记录离职结算日志，消息中心返回处理结果。

### 5.3 撤销调休假结算

1. 前端先调用校验接口，后端返回：
   1. `total`：选中数量；
   2. `success`：可撤销数量；
   3. `ignore`：历史已撤销数量；
   4. `fail`：考勤周期已封存数量。
2. 原型展示上述校验结果，用户确认后只提交可处理记录。
3. 后端再次根据考勤周期封存状态过滤记录，取得未撤销且未封存的结算明细。
4. 将结算汇总和明细设为无效，删除对应 OT 结算明细。
5. 按结算明细恢复调休假日明细：已转加班费额度减少，可休额度恢复；同时刷新周期和年度汇总。
6. 写入调休假撤销结算日志，消息中心返回处理结果。

## 6. 病假结算

### 6.1 离职结算

1. 前端要求先勾选病假余额统计记录。
2. 提交前先检查审批中的病假单/销假单（后端代码中称“在途单据”）。这些单据审批完成后可能继续扣减或恢复额度，导致当前结算数不是最终数。存在时不强制阻断，页面提供“暂不结算 / 仍要结算”。
3. 后端将选中记录分为：未离职、已结算、“已离职且未结算”三类，只处理第三类。
4. 查询员工假勤方案和病假配置，按“离职结算规则”处理：
   1. 配置为“余额清零”：结算额度写 0，可休额度清 0；
   2. 配置为“按入职天数结算”：满足配置条件时，结算额度取当前可休额度；不满足时，结算额度写 0。两个分支都将可休额度清 0。
5. 不论结算额度是否为 0，均将“是否结算”设为是，“结算额度所属日期”设为员工离职日期。
6. 更新病假统计记录，写入病假结算日志，并生成未离职/已结算/成功结算的反馈明细。
7. 结果通过消息中心返回。

**代码核对风险**

代码注释将入职天数定义为“离职日期 - 入职日期 + 1”，实际代码使用 `DateUtil.betweenDay`。该方法是否包含首尾日取决于当前 Hutool 版本和调用参数，开发应用生产依赖版本做边界用例核对，避免入职天数差 1 天。

### 6.2 撤销病假结算

1. 前端传入选中病假统计记录 ID。
2. 后端计算每个员工在“结算额度所属日期”对应考勤周期的封存状态。
3. 未结算记录和所属考勤周期已封存的记录不处理。
4. 对可撤销记录：
   1. 结算额度清 0；
   2. 结算标识改为否；
   3. 结算额度所属日期清空；
   4. 按该次入职周期下的病假年度汇总当前可休额度合计，重新计算并恢复统计记录的可休额度。
5. 写入病假撤销结算日志，生成已封存/未结算/成功撤销的反馈明细，通过消息中心返回。

## 7. 汇总、明细和日志

### 7.1 年假

- 结算汇总：`POST /api/attendance/vacationSettlementSummary/pageList`。
- 结算明细：`POST /api/attendance/vacationSettlementDetail/pageList`。
- 日志列表：`POST /api/attendance/annualLeaveSettlementLog/pageList`。
- 日志变更明细：`POST /api/attendance/annualLeaveSettlementLog/getLogDetailById`。
- 点击汇总的“结算总额度/明细”时，前端切换到结算明细页签，并带入员工、结算类型和结算所属日期查询。

### 7.2 调休假

- 结算汇总：`POST /api/attendance/attendance-compensatory-leave-settlement-summary/pageList`。
- 结算明细：`POST /api/attendance/attendance-compensatory-leave-settlement-detail/pageList`。
- 日志列表：`POST /api/attendance/attendance-compensatory-leave-settlement-log/pageList`。
- 点击汇总的“可休总额度/明细”时，前端切换到结算明细页签，并带入员工和该汇总行的考勤日期范围。

### 7.3 病假

新的病假结算页只保留结算统计列表和结算/撤销操作，不增加“结算汇总/年度汇总”子页签和行日志入口。后端仍保留原有病假日志接口，供原 OEHR 病假额度页使用，本次不暴露在新页面。

### 7.4 查询、重置、页签、导出和导出设置

| 按钮/交互 | 前端处理 | 后端处理 |
| --- | --- | --- |
| 查询 | 取当前页签下的条件、回到第 1 页后发起请求 | 年假汇总调 `/vacationSettlementSummary/pageList`；年假明细调 `/vacationSettlementDetail/pageList`；调休汇总调 `/attendance-compensatory-leave-settlement-summary/pageList`；调休明细调 `/attendance-compensatory-leave-settlement-detail/pageList`；病假调 `/attendanceSickLeaveStatistical/pageList` |
| 重置 | 清空输入项，下拉项恢复页面默认值；只改变条件，不立即请求后端 | 用户再点“查询”时才用重置后的条件调分页接口 |
| 结算汇总/结算明细页签 | 切换查询条件和列表；不将汇总行在前端拆为明细 | 分别调汇总或明细分页接口 |
| 汇总行“明细”/额度热区 | 切换到明细页签，回填员工、结算类型、所属日期或考勤日期范围 | 用回填条件调对应明细分页接口，不从当前 DOM 数据反推明细 |
| 日志 | 打开日志弹窗，支持按操作时间、操作人查询和重置 | 年假调 `/annualLeaveSettlementLog/pageList`；调休调 `/attendance-compensatory-leave-settlement-log/pageList`；病假新页面不展示行日志 |
| 导出 | 提交当前页签、查询条件和导出字段配置，显示任务已提交 | 年假调 `/vacationSettlementSummary/export`；调休调 `/attendance-compensatory-leave-settlement-summary/export`；病假调 `/attendanceSickLeaveStatistical/export`；后端按查询条件重查全量数据，不只导出当前页 DOM |
| 导出设置 | 展示当前页可导出字段，用户选择后用于后续导出 | 现有结算 Controller 只有导出接口，字段配置由平台通用导出配置/MenuRouter 能力承接，不在三个结算模块内新增业务接口；生产分支需再核对通用配置接口 |

导出接口的成功意义与结算不同：导出是读取当前数据并生成文件，不修改结算、额度或日志数据。

## 8. 原型操作反馈

| 场景 | 页面处理 |
| --- | --- |
| 未勾选即撤销 | 不调用后端，页面提示“请先勾选数据”或调休现有文案“请至少选择一条数据” |
| 必填字段空 | 不提交，保留已填内容，标记全部空必填字段，字段下方提示“必填项不能为空”并定位第一个错误项 |
| 病假存在审批中的休假/销假单 | 说明后续审批可能继续扣减或恢复额度；选“暂不结算”时不提交，选“仍要结算”后继续结算 |
| 调休撤销前校验存在不可处理数据 | 展示选中/可撤销/已撤销/已封存数量，确认后排除不可处理记录 |
| 接口已接受结算/撤销任务 | 展示“结算任务已提交”，明确最终结果需前往消息中心查看，不把接口受理成功表述为结算全部成功 |

## 9. 开发接口契约

### 9.1 年假结算

`AttendanceVacationSettlementDTO` 是结算和撤销的公用请求对象。

| 页面字段 | DTO 字段 | 过期结算 | 离职结算 | 撤销结算 |
| --- | --- | --- | --- | --- |
| 结算类型 | `settlementType` | `1` | `2` | 不需要 |
| 划分区域 | `divideAreaCode` | 必传 | 必传 | 不需要 |
| 员工 | `empNoSet` | 选填 | 选填 | 不需要 |
| 组织 | `orgCodeSet` | 选填 | 选填 | 不需要 |
| 年度 | `yearList` | 必传，传入具体年份集合 | 不作为页面条件 | 不需要 |
| 结算额度所属日期 | `settlementBelongDateStr` | 必传，`yyyy/MM/dd` | 前端不传人工日期，后端取离职日期 | 不需要 |
| 勾选结算记录 | `idSet` | 不需要 | 不需要 | 必传汇总记录 ID |

**后端事务与幂等要求**

- 不能仅根据页面的“是否已结算”判断；必须在服务端重新查询有效汇总/明细，再计算本次差额。
- 单个员工的结算汇总、各年度明细、年假余额回写和日志必须同一事务；任一步失败，该员工整体回滚。
- 撤销不是直接把原结算数值加回可休额度；必须作废原结算，再根据剩余有效结算明细重算过期/离职结算额度及可休额度。
- 结算任务允许员工级部分成功，反馈文件要记录员工、成功/失败和失败原因，不得只返回一个总体成功标识。

### 9.2 调休假结算

**余额结算请求 `AttendanceCompensatoryLeaveBalanceSettlementDTO`**

| 页面字段 | DTO 字段 | 规则 |
| --- | --- | --- |
| 考勤周期 | `cycleId` / `cycleName` | `cycleId` 必传；名称用于展示和反馈 |
| 考勤时间段 | `cycleDetailIds` / `attendanceTimePeriods` | 明细 ID 必传；现有处理实际按单个周期时段结算 |
| 员工 | `empNo` | 与组织二选一或均不传 |
| 组织 | `orgCodes` | 与员工二选一或均不传 |

**离职结算请求 `AttendanceCompensatoryLeaveDimissionSettlementDTO`**

- `empNo`：待结算员工工号集合。页面必须选择员工，后端仍需重新校验离职单、最后工作日、考勤周期和排班，不接受前端传入这些结果。

**撤销请求 `AttendanceCompensatoryLeaveBalanceCancelSettlementDTO`**

- `cycleCacelSettlements`：按员工和考勤周期组装的待撤销数据。每项包含 `empNo`、`attendanceCycleId`、`attendanceCycleDetailId`、`cycleName`、`attendanceCycleStartDate`、`attendanceCycleEndDate`、`settlementType`。
- 前端必须先使用同一份请求调用 `/cancelSettlement/verify`，只将校验结果用于告知用户；正式撤销时后端必须再次校验封存和有效状态，防止校验后数据变化。
- 恢复逻辑以原调休假日明细与结算明细的关联为依据：减少已转加班费额度、恢复可休额度，然后重算周期和年度汇总；不能只更新汇总表。

### 9.3 病假结算

`AttendanceSickLeaveSettleDTO` 同时用于离职结算和撤销结算。

| 字段 | 规则 |
| --- | --- |
| `ids` | 必传，传入病假统计记录 ID，不是员工 ID |
| `type` | 必传，`1` 表示单个，`2` 表示批量 |

**调用顺序**

1. 离职结算前用 `{ ids }` 调用 `/checkSickApply`。
2. 返回存在审批中病假/销假单时，前端做风险告知；用户选“暂不结算”则不再调结算接口，选“仍要结算”则继续调用 `/dimissionSettlement`。
3. 后端根据有效离职数据和病假方案自行决定结算额度，前端不传“应结算额度”、离职日期或入职天数。
4. 撤销时直接使用 `{ ids, type }` 调用 `/cancelSettlement`；后端重查是否已结算及所属考勤周期是否封存。

**数据回写边界**

- 结算额度所属年度由 `settlementQuotaBelongDate` 的年份确定；现有代码将该日期写为员工离职日期。
- 撤销时恢复的可休额度，取同一用工记录/入职日期下病假年度汇总当前可休额度合计，不是将原 `settlementQuota` 简单加回。
- 任务接口返回成功仅代表受理；未离职、已结算、已封存等记录都可能在异步任务中被跳过，必须从消息中心反馈文件获取最终结果。
